# ai-tool-access-requests 開発サマリー

## 3行要約

- Django / PostgreSQL を用いて、エンタープライズ向け AI ツールの利用申請と承認のための最小構成の内部業務アプリを実装しています。
- 単なる CRUD ではなく、申請者・レビュワー・admin の責務分離、自己レビュー禁止、重複申請防止、閲覧専用 admin など、業務ルールを意識した設計を重視しています。
- 小さな MVP として公開しつつ、コアワークフローを壊しにくくするためのテストとドキュメント整備まで含めて、実務に近い開発の流れを示すことを目的としています。

## なぜこの題材なのか

今回の題材は、エンタープライズ向け AI ツールの利用申請と承認フローです。  
AI ツールの導入や利用可否は、単なる設定画面ではなく、申請、審査、承認、却下、閲覧権限、運用管理といった複数の要素が絡むため、最小構成でも業務アプリとしての設計力を示しやすい題材だと考えました。

また、通知、監査ログ、多段承認、API 化などはあえて v0.1.0 の対象外にし、まずはコアフローを小さく成立させることを優先しています。  
個人開発では機能を盛り込みすぎて公開が遅れがちですが、このリポジトリでは最小実装を先に整え、その上で意味のある改善を積み上げる方針を採っています。

## このリポジトリで特に見てほしい点

### 1. 申請者向け画面とレビュワー向け画面を明確に分けていること

このアプリでは、申請者向けの `/requests/<pk>/` と、レビュワー向けの `/reviews/<pk>/` を明確に分離しています。  
単に画面を分けるだけでなく、「誰がどの画面を使うのか」「どの操作をどこで実行するのか」をはっきりさせることで、ワークフロー上の責務を見えやすくしています。

### 2. 自己レビュー禁止や重複申請防止を複数レイヤで扱っていること

業務ルールは、1か所にまとめて書けばよいわけではありません。  
このリポジトリでは、たとえば自己レビュー禁止や重複する `pending` 申請の防止について、ビュー、フォーム、モデル、データベース制約の役割を分けて扱っています。

これは、画面上の見た目だけではなく、直接 `POST` や将来の変更を含めてもルールが崩れにくい状態を目指しているためです。

### 3. admin を閲覧中心に限定していること

Django admin は便利ですが、業務ワークフローの本体を admin に寄せると、意図しない操作経路が増えやすくなります。  
そのため、このアプリでは `AITool` は admin で運用管理できる一方、`AccessRequest` は閲覧専用に寄せ、承認・却下の実行は通常画面側の専用レビュー UI に限定しています。

### 4. 小さな MVP でもテストまで含めて整えていること

このリポジトリでは、v0.1.0 の MVP として必要十分な automated tests を揃えることを重視しました。  
フォーム、ルート、権限、レビュー実行、モデル整合性、データベース制約、admin の安全性を責務ごとに分けて確認し、通常のリファクタや機能変更でコア業務ルールが壊れにくい状態を目指しています。

## 開発方針

このリポジトリは、以下の方針で整えています。

- **小さく公開し、意味のある改善を積み上げる**  
  最初から過剰に広げず、MVP を成立させた上で、必要な改善を小さく積み上げる方針です。

- **権限境界と業務ルールを曖昧にしない**  
  誰が何を見られ、何を実行できるのかを、ルート、ビュー、フォーム、admin の各層で明確に保つことを重視しています。

- **実装・テスト・文書をセットで整える**  
  コードだけでなく、README、公開サマリ、テストまで含めて、保守しやすく説明しやすい状態に持っていくことを意識しています。

- **Django built-ins を中心に組み立てる**  
  カスタム実装を過剰に増やさず、まずは Django 標準機能をどう実務的に使うかを示すことを優先しています。

## v0.1.0 までで整えたこと

v0.1.0 までの段階で、次のような要素を揃えています。

- AI ツールカタログの閲覧
- 利用申請の作成
- 申請者による自分の申請一覧・詳細の確認
- レビュワーによる保留中申請の承認・却下
- Django admin によるツール管理
- `AccessRequest` の閲覧専用 admin
- 申請・レビュー・admin 境界を押さえる automated tests
- 最小限の CSS を含む、役割の違いが分かる UI

この段階では、Docker、通知、監査ログ、多段承認、公開 API などは意図的に入れていません。  
まずは「小さいが業務アプリとして成立している」ことを明確にすることを優先しています。
