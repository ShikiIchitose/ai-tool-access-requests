# ai-tool-access-requests

エンタープライズ向け AI ツールの利用申請とレビューを行うための、最小構成の Django + PostgreSQL 製内部ワークフローアプリケーションです。

このリポジトリは、Django を用いた実践的なバックエンド基礎力を示すためのポートフォリオ作品です。認証、認可、リレーショナルデータモデリング、フォームバリデーション、クラスベースビュー、運用を意識した admin 設計、そしてコア業務ルールを変更による退行から守るためのテストを主な題材としています。スコープは意図的に小さく絞っていますが、単なる CRUD デモではなく、現実的な社内業務アプリケーションに近いワークフローとなるよう設計しています。

以下のスクリーンショットは、このアプリケーションにおける 2 つの主要な利用者の視点、すなわち申請者向けの申請追跡画面と、レビュワー向けのレビュー業務画面を示しています。

## ポートフォリオ用デモアクセス

ログインページには、通常の username/password フォームに加えて、**ポートフォリオ用デモアクセス** のボタンを用意しています。

公開デモで利用できるロールは次の 2 つです。

- **デモ申請者**
  - 有効な AI ツールを閲覧できる
  - 新しい利用申請を提出できる
  - 申請者向けの申請履歴を確認できる

- **デモレビュワー**
  - レビュワー専用のレビューキューを開ける
  - 保留中の申請を確認できる
  - 専用のレビュー UI から承認または却下を実行できる

補足:

- 公開デモで触れられるのは、申請者視点とレビュワー視点のみです。
- **Django admin は公開デモの対象に含めていません。**
- このデモアクセス導線は、ポートフォリオ閲覧者が試しやすくなるよう追加したものであり、本番向けの認証設計として提示しているものではありません。

## Seed 済みデモデータ

公開デモでは、主要なフローをすぐ確認できるように、小さな seed データセットを用意しています。

含まれているデモ状態は次の通りです。

- 次の AI ツールが active 状態で存在する
  - ChatGPT Enterprise
  - Claude Enterprise
  - Gemini Enterprise
- レビュワーから見える `pending` の申請が少なくとも 1 件ある
- `approved` の申請が少なくとも 1 件ある
- `rejected` の申請が少なくとも 1 件ある

特に、レビュワーから見える `pending` 申請は、デモレビュワーでログインした直後にレビューキューがすぐ使えるよう、意図的に seed しています。

## デモの試し方

### 申請者フロー

1. 公開デモを開く。
2. `/login/` で **Continue as demo requester** を選ぶ。
3. ツールカタログを閲覧する。
4. active なツールに対して新しい利用申請を作成する。
5. **My requests** を開き、提出済みの申請とその現在の状態を確認する。

### レビュワーフロー

1. 公開デモを開く。
2. `/login/` で **Continue as demo reviewer** を選ぶ。
3. レビューキューを開く。
4. すぐにレビュー可能な `pending` 申請を確認する。
5. 専用のレビュワー向け画面から承認または却下を実行する。

## プロジェクト概要

このアプリケーションでは、以下を行えます。

- 認証済みユーザーが社内向け AI ツールカタログを閲覧できる
- 申請者が有効な AI ツールに対して利用申請を提出できる
- 申請者が自分の提出した申請だけを閲覧できる
- レビュワーが保留中の申請を確認し、承認または却下できる
- Django admin は運用保守と安全な閲覧のために使用し、承認・却下ワークフローを実行する場としては使わない

ドメインモデルは意図的に最小構成にしています。

- Django 組み込み `User`
- `AITool`
- `AccessRequest`

ロールも明示的に定義しています。

- **申請者 (`requester`)**: 通常の認証済みユーザー
- **レビュワー (`reviewer`)**: `Group(name="reviewer")` に所属するユーザー
- **admin 担当者 (`admin operator`)**: Django admin にアクセスするために `is_staff=True` を持つユーザー
- **システム管理者 (`system owner`)**: システム全体権限を持つ superuser

この分離は意図的なものです。業務ワークフロー上のロールと、Django のシステムフラグは、関連はあっても別の責務として扱っています。

## コアワークフロー

1. 認証済みユーザーが有効な AI ツールカタログを閲覧する。
2. ユーザーが目的と業務上の必要性を記載して利用申請を提出する。
3. 申請者は、自分の提出済み申請と現在の状態のみを閲覧できる。
4. レビュワーは、自分自身の申請を除いた保留中申請のレビューキューを確認する。
5. レビュワーは専用のレビュー UI から申請を承認または却下する。
6. Django admin は、ツールカタログの管理と申請レコードの安全な閲覧に使用する。

## 主要な業務ルール

このプロジェクトは意図的に小さく作っていますが、いくつか重要なワークフロールールを含んでいます。

- **申請者向けルートとレビュワー向けルートを分離**
  - `/requests/<pk>/` は申請者本人のみ
  - `/reviews/<pk>/` はレビュワー専用

- **自己レビューは禁止**
  - レビュワーは自分が提出した申請をレビューできない
  - 自分自身の保留中申請はレビューキューから除外される
  - 自己レビューに対する直接アクセスや `POST` によるレビュー実行は拒否される

- **レビュー可能なのは `pending` の申請のみ**
  - 一度承認または却下された申請は再レビューできない

- **重複する保留中申請を防止**
  - 同一ユーザーが同一ツールに対して複数の `pending` 申請を同時に持つことはできない
  - この制約はフォーム層とデータベース層の両方で守られる

- **無効化されたツールは申請できない**
  - 無効なツールは申請者向け画面には表示されない
  - 手動 `POST` で送信された場合もサーバー側で拒否される

- **admin は閲覧中心**
  - `AITool` は Django admin 上で運用管理される
  - `AccessRequest` は admin 上では閲覧専用として扱う
  - 申請の承認・却下は admin では実行しない

このプロジェクトの狙いは、単に CRUD を実装することではなく、権限制御の境界とワークフローの安全性を丁寧に扱えることを示す点にあります。

## テストスイートが重要な理由

このリポジトリには、コードの変更に伴って壊れやすい部分に焦点を当てた、**最小限だが意味のある自動テストスイート**があります。

目的は、広く浅いカバレッジではありません。代わりに、以下のコア業務ルールを守ることに重点を置いています。

- フォームバリデーション
- 申請者向けルートとレビュワー向けルートの分離
- 権限境界
- 自己レビュー禁止
- 無効ツールの扱い
- モデル整合性
- データベース制約による重複 `pending` 防止
- 閲覧専用 admin の挙動
- ポートフォリオ用デモログインの挙動と、デプロイ環境における前提状態

テストは責務ごとに整理しています。

- `test_forms.py`
  - 入力バリデーション
  - 無効ツールの拒否
  - 重複する保留中申請の拒否
  - 却下時コメント必須

- `test_views.py`
  - ルート保護
  - ロールに応じたアクセス制御
  - 申請者とレビュワーのフロー境界
  - 承認・却下ワークフローの挙動
  - 再レビュー防止
  - 自己レビュー防止

- `test_models.py`
  - `status` の選択肢
  - モデル整合性バリデーション
  - 重複 `pending` 申請に対するデータベース制約の挙動

- `test_admin.py`
  - Django admin 上での権限境界
  - `AccessRequest` の閲覧専用挙動
  - admin 経由でのワークフローバイパス防止

- `test_auth_demo.py`
  - デモログインページの表示
  - 申請者 / レビュワーのデモログイン挙動
  - 安全な `next` リダイレクト処理
  - feature 無効時や demo user 不在時の挙動
  - `ensure_demo_state` による状態整備の前提確認

つまり、このテストスイートは、通常のリファクタや機能変更によって申請作成、レビュー実行、権限境界、admin の安全性、あるいはポートフォリオ用デモアクセス導線が壊れる可能性を下げることを目的としています。

## アーキテクチャノート

### 最小ドメインモデル

このプロジェクトでは、`ForeignKey` を中心とした小さなリレーショナルモデルを採用しています。

- `AccessRequest.requester -> User`
- `AccessRequest.reviewed_by -> User`
- `AccessRequest.ai_tool -> AITool`

これにより、初期リリースを把握しやすく保ちながら、現実的な申請・レビューのワークフローを表現できます。従業員プロフィールやレビュワーの担当範囲、分類タグなどの将来拡張は意図的に後回しにしています。

### レイヤごとの責務

このプロジェクトでは、責務を各レイヤに意図的に分けています。

- **モデル層 / データベース層**
  - 構造的整合性
  - 制約
  - 参照整合性

- **フォーム層**
  - 入力バリデーション
  - ユーザー向けフィードバックのための重複検出
  - 却下時コメント必須

- **ビュー層**
  - 認証と認可
  - オブジェクト単位のアクセス制御
  - ワークフロー実行
  - レビュー決定の安全な処理

- **admin 層**
  - 運用上の可視性
  - カタログ管理
  - ワークフロー実行ではなく安全な閲覧

この分離は重要です。バックエンド設計とは、単にページを動かすことではなく、どのルールをどのレイヤに置くべきかを適切に設計することでもあるからです。

## ローカルセットアップ

### 前提条件

- Python 3.13
- ローカルで動作する PostgreSQL
- `uv`

### 依存関係のインストール

```bash
uv sync
```

### 環境変数の設定

`.env.example` をもとにローカル用の環境変数ファイルを作成し、手元の環境に合わせて値を設定してください。

環境変数の読み込み方法は各自の運用に委ねています。たとえば、シェルから読み込む簡単な方法としては次の様な方法があります。

```bash
cp .env.example .env.local
set -a
source .env.local
set +a
```

基本データベース関連設定は次の通りです。

```env
DB_NAME=your_db_name
DB_USER=your_db_user
DB_PASSWORD=your_db_password
DB_HOST=127.0.0.1
DB_PORT=5432
DJANGO_SECRET_KEY=replace-this-with-a-real-secret
```

### マイグレーションの適用

```bash
uv run python manage.py migrate
```

### スーパーユーザーの作成

```bash
uv run python manage.py createsuperuser
```

### 開発サーバーの起動

```bash
uv run python manage.py runserver
```

## レビュワーと admin の初期設定

Django admin にログインした後、以下を行います。

1. `reviewer` という名前のグループを作成する
2. レビュワーとして使うユーザーを作成または選択する
3. そのユーザーを `reviewer` グループに追加する
4. Django admin へアクセスさせたいユーザーにのみ `is_staff=True` を付与する
5. admin 上で閲覧権限が必要な場合は、組み込みのモデル閲覧権限を付与する

このプロジェクトでは、`is_staff` だけをレビュワー権限と同一視しません。レビュー権限は admin アクセスではなく、業務ワークフロー上のロールに属するものとして扱います。

## サンプル AI ツールの作成

サンプルツールは Django admin から作成できます。

推奨する例は以下の通りです。

- `code`: URL-safe な安定 `slug`
- `name`: 製品名
- `vendor`: ベンダー名
- `description`: 短い社内向け説明
- `homepage_url`: 公式製品ページ
- `is_active`: 有効 / 無効フラグ

通常運用では、ツール削除ではなく `is_active=False` による**論理的な無効化**を前提にしています。

## デモ用デプロイメモ

デプロイ環境でポートフォリオ用デモフローを有効にするには、次の環境変数を設定します。

```env
ENABLE_DEMO_LOGIN=true
DEMO_REQUESTER_USERNAME=demo-requester
DEMO_REVIEWER_USERNAME=demo-reviewer
```

デプロイ後は、次のコマンドでデモ状態を作成または修復します。

```bash
uv run python manage.py ensure_demo_state
```

このコマンドにより、demo users、reviewer group の所属状態、active な demo tools、そして公開デモに必要な最小限の申請状態が整備されます。

## テストの実行

完全な自動テストスイートは次で実行できます。

```bash
uv run pytest
```

任意の追加チェック:

```bash
uv run python manage.py check
```

このテスト群は、見た目の確認ではなく、コアワークフローの安全性に焦点を当てています。主に次のような退行を検知することを目的としています。

- 申請作成ルール
- レビュー権限境界
- 自己レビュー禁止
- モデルおよびデータベース整合性
- admin 側の安全性
- デモログイン機能が有効な場合と無効な場合の両方の挙動

## スコープと非対象

このプロジェクトのスコープは、最小かつ一貫したものに保つため、意図的に制限しています。

### v0.1.0 に含めるもの

- AI ツールカタログの閲覧
- 利用申請の作成

- セルフサインアップ
- メール通知
- Slack 通知
- 多段承認
- 専用の監査ログテーブル
- 外部 API 連携
- 公開 API
- Django REST Framework
- Docker と Docker Compose
- JavaScript に大きく依存するリッチ UI
- カスタムユーザーモデル

これらを除外しているのは意図的です。このプロジェクトの目的は、機能数を最大化することではなく、現実的なバックエンド境界を持つ、規律ある最小実用製品を示すことです。
